## Executive Summary

The Habits App has a solid architectural foundation (hexagonal backend, Zustand + service worker frontend) and many UX features already implemented well — particularly optimistic completion toggling, confetti celebrations, Web Audio API feedback, and local-first caching. However, the audit identified **42 discrete UX issues** across 4 severity levels:

| Severity | Count | Description |
|----------|-------|-------------|
| 🔴 P0 - Critical | 5 | Directly breaks documented UX rules or causes data loss |
| 🟠 P1 - High | 11 | Significant negative impact on user experience |
| 🟡 P2 - Medium | 15 | Noticeable friction or inconsistency |
| 🔵 P3 - Low | 11 | Polish, best practices, future-proofing |

The three most impactful themes are:
1. **Incomplete Local-First/Offline experience** — Only completion toggling and counter updates work offline; task creation, updates, deletion, and reordering are blocked
2. **Accessibility gaps** — Missing ARIA attributes, no keyboard navigation for custom controls, zoom disabled, no focus traps in modals/panels
3. **Performance risk from monolithic App.tsx** — Timer ticking every second causes full-app re-renders

## Critical Issues (P0)

### P0-1: Offline Task Creation/Update/Delete Is Blocked, Not Queued

> [!CAUTION]
> **Directly violates** GEMINI.md §6 Rule 1: *"Las interacciones del usuario (crear, completar, borrar tareas) deben reflejarse inmediatamente en la interfaz (0ms de latencia percibida)"*

**Source:** [useHabitStore.js](file:///Users/jaimehmol/src/habits-app/frontend/src/store/useHabitStore.js), [App.tsx](file:///Users/jaimehmol/src/habits-app/frontend/src/App.tsx)
**Current behavior:** When offline, `addTask`, `updateTask`, `deleteTask`, and `reorderTasks` trigger a native `alert()` blocking the user and preventing the action entirely. Only `toggleComplete`, `increment`, and `decrement` are optimistically queued.
**Impact:** Users who go offline (common on mobile PWA) cannot perform basic task management — the core value proposition of the app breaks.
**Solution:**
1. Extend the `syncQueue` in `useHabitStore` to support all mutation types (`ADD_TASK`, `UPDATE_TASK`, `DELETE_TASK`, `REORDER`)
2. Generate client-side UUIDs for new tasks (see P0-3) to enable offline creation
3. Replace `alert()` calls with non-blocking toast notifications
4. Apply mutations optimistically to local Zustand state first, sync in background

### P0-2: Native `alert()` Breaks Dark Theme Immersion

> [!CAUTION]
> **Directly violates** GEMINI.md §6 Rule 3: *"Nunca uses elementos nativos (como `<select>`) que rompan la inmersión del diseño oscuro"*

**Source:** [useHabitStore.js](file:///Users/jaimehmol/src/habits-app/frontend/src/store/useHabitStore.js) (offline error handling)
**Current behavior:** `alert(translations[lang].offline_action)` displays a native OS dialog that breaks the dark theme and blocks the UI thread.
**Impact:** Jarring visual break, prevents any user interaction until dismissed, feels like a crash on mobile.
**Solution:** Replace with the existing `NotificationToast` component using `type='warning'`.

### P0-3: Integer Auto-Increment IDs Prevent Offline Task Creation

**Source:** [models.py](file:///Users/jaimehmol/src/habits-app/backend/src/domain/models.py) (Task model), backend API
**Current behavior:** Task IDs are auto-incremented integers generated by the database. If a task is created offline, it has no ID until synced, making it impossible to reference (e.g., to complete or edit it before sync).
**Impact:** Fundamental blocker for true local-first architecture as mandated by GEMINI.md §6 Rule 1.
**Solution:**
1. Add a `uuid` field (string) to the Task model, generated client-side
2. Use UUID as the primary key or as a secondary unique identifier for deduplication
3. Backend should handle upsert logic: if UUID already exists, skip creation
4. Requires an Alembic migration

### P0-4: Full-App Re-render Every Second During Active Timer

**Source:** [App.tsx](file:///Users/jaimehmol/src/habits-app/frontend/src/App.tsx), [useHabitStore.js](file:///Users/jaimehmol/src/habits-app/frontend/src/store/useHabitStore.js)
**Current behavior:** When a focus timer is active, `App.tsx` subscribes to a `setInterval` ticking every 1 second. Since `App.tsx` is the root component managing all state, this causes the **entire component tree** (all 4 columns, all task cards, header, panels) to re-render every second.
**Impact:** Severe performance degradation, battery drain on mobile, potential dropped frames during drag-and-drop or swipe gestures.
**Solution:**
1. Extract the timer display into an isolated component with its own subscription to the timer state
2. Use Zustand selectors (`useHabitStore(state => state.activeTimer)`) to limit re-renders to only the components that need timer data
3. Consider `React.memo()` for `Column` and `TaskCard` components
4. Long-term: decompose `App.tsx` into smaller route-level components

### P0-5: Invalid Date Validation Missing (Feb 30, Apr 31)

**Source:** [models.py](file:///Users/jaimehmol/src/habits-app/backend/src/domain/models.py), [InlineTaskForm.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/InlineTaskForm.jsx)
**Current behavior:** `target_day` allows 1-31 and `target_month` allows 1-12, but there's no cross-validation. A user can set a task for "February 30th" or "April 31st", which causes the reminder scheduler to misbehave or crash.
**Impact:** Data corruption, silent reminder failures, potential backend crashes.
**Solution:**
1. Add a Pydantic model validator that cross-checks `target_day` against `target_month` using `calendar.monthrange()`
2. Add the same validation in `InlineTaskForm.jsx` when the user selects day/month
3. Show inline validation error: "Invalid date for this month"

## High-Priority Issues (P1)

### P1-1: No Error Boundary — App Crashes Show Blank Page

**Source:** [main.tsx](file:///Users/jaimehmol/src/habits-app/frontend/src/main.tsx)
**Current behavior:** No `<ErrorBoundary>` wraps the `<App />` component. Any uncaught JS error in any component (including drag-and-drop edge cases or malformed API data) crashes to a white screen.
**Impact:** Complete loss of app functionality with no recovery path. User must manually reload.
**Solution:** Wrap `<App />` in a React Error Boundary that renders a styled error page with a "Reload" button, matching the dark theme.

### P1-2: Accessibility — Custom Controls Lack ARIA Attributes

**Source:** Multiple components
**Files affected:**
- [InlineTaskForm.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/InlineTaskForm.jsx) — Custom `Dropdown` missing `aria-expanded`, keyboard navigation, focus trapping
- [PeriodicReviewModal.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/PeriodicReviewModal.jsx) — Missing `aria-modal="true"`, focus trap, `role="dialog"`
- [ReminderPanel.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/ReminderPanel.jsx) — Missing `role="dialog"`, focus trap, `aria-expanded` on trigger
- [NotificationToast.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/NotificationToast.jsx) — Missing `role="alert"` or `aria-live="assertive"`
- [TaskCard.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/TaskCard.jsx) — Icon buttons lack `aria-label`
- [LoadingSkeleton.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/LoadingSkeleton.jsx) — Missing `aria-busy="true"`

**Impact:** Screen reader users cannot effectively use the application. Custom dropdowns, modals, and panels are invisible or confusing to assistive technology.
**Solution:** Systematic pass through all components adding proper ARIA roles, labels, and keyboard handlers. Consider using Radix UI or Headless UI primitives for modals, dropdowns, and panels.

### P1-3: Viewport Zoom Disabled — WCAG Violation

**Source:** [index.html](file:///Users/jaimehmol/src/habits-app/frontend/index.html) — `maximum-scale=1.0, user-scalable=no`
**Impact:** Visually impaired users cannot pinch-to-zoom, violating WCAG 1.4.4 (Resize Text). Reported as an accessibility barrier by automated testing tools.
**Solution:** Remove `maximum-scale=1.0` and `user-scalable=no` from the viewport meta tag.

### P1-4: Sync Queue Not Exposed — No Offline Status Indicator

**Source:** [useHabitStore.js](file:///Users/jaimehmol/src/habits-app/frontend/src/store/useHabitStore.js), [App.tsx](file:///Users/jaimehmol/src/habits-app/frontend/src/App.tsx)
**Current behavior:** Pending offline actions are stored in `syncQueue` but there is no UI element showing the user how many actions are pending or whether sync is in progress.
**Impact:** Users have no confidence that their offline changes will persist. If they close the browser before sync completes, data is lost silently. This is especially critical given that the SW does not use the native `SyncManager` API.
**Solution:**
1. Add a subtle status badge/pill in the header (e.g., "3 changes pending" with a sync icon)
2. When online and syncing, show a progress indicator
3. On sync completion, show a brief success toast
4. On sync failure, show a persistent warning with retry action

### P1-5: `GET /reminders/` Triggers O(N) Auto-Sync on Every Fetch

**Source:** Backend reminder router/service
**Current behavior:** Every call to `GET /reminders/` executes `sync_all_task_reminders()`, which loops through all tasks, performing individual DB queries for each to ensure reminder consistency.
**Impact:** As the task count grows, this endpoint becomes progressively slower, directly violating the "Zero-Loading-Screen" mandate. On a device with 100+ tasks, this could add seconds of latency.
**Solution:**
1. Decouple the sync from the read path — run it as a background job (e.g., on task create/update) or a periodic cron
2. Use bulk SQL operations instead of per-task queries
3. Add database indexes on `task_id` in the reminders table

### P1-6: No Bulk Sync Endpoint for Offline Queue Replay

**Source:** Backend API, [useHabitStore.js](file:///Users/jaimehmol/src/habits-app/frontend/src/store/useHabitStore.js)
**Current behavior:** When connectivity returns, the frontend replays queued actions one at a time (N individual HTTP requests). With 20 offline completions, this means 20 sequential API calls.
**Impact:** Slow sync, increased chance of partial failure, battery drain on mobile.
**Solution:** Create a `POST /api/tasks/batch-sync` endpoint that accepts an array of mutations and processes them atomically.

### P1-7: No Task Completion History Endpoint

**Source:** Backend [models.py](file:///Users/jaimehmol/src/habits-app/backend/src/domain/models.py), backend API
**Current behavior:** The `TaskCompletionLog` table is populated on every completion, but **there is no GET endpoint** exposing this data to the frontend. The frontend cannot display streaks, heatmaps, or historical statistics.
**Impact:** Missed opportunity for a key habit-tracking feature. Users can't see their progress over time, reducing long-term engagement and motivation.
**Solution:** Create `GET /api/tasks/{id}/history` and `GET /api/tasks/stats` endpoints.

### P1-8: Monolithic App.tsx (~476 lines)

**Source:** [App.tsx](file:///Users/jaimehmol/src/habits-app/frontend/src/App.tsx)
**Current behavior:** Single component manages: auth state, task CRUD, drag-and-drop context, swipe gesture handling, timer subscriptions, language switching, panel/modal visibility, layout rendering, and PWA install prompts.
**Impact:** High coupling, difficult to test, difficult to modify. Any change risks regressions. Performance is degraded because state changes in any area trigger re-renders of the entire tree.
**Solution:** Progressive decomposition:
1. Extract `AuthScreen` component
2. Extract `BoardHeader` component
3. Extract `KanbanBoard` component (wrapping Columns)
4. Extract `TimerOverlay` component
5. Use `React.lazy` for modal/panel components

### P1-9: Drag-and-Drop + Touch Swipe Conflict

**Source:** [App.tsx](file:///Users/jaimehmol/src/habits-app/frontend/src/App.tsx)
**Current behavior:** Manual `onTouchStart`, `onTouchMove`, `onTouchEnd` handlers for mobile column swiping coexist with `@hello-pangea/dnd` drag-and-drop on the same DOM container.
**Impact:** Touch events may bubble unpredictably, causing: accidental column swipes when trying to drag a card, dropped frames during gestures, or phantom card movements.
**Solution:**
1. Add gesture discrimination logic (e.g., vertical drag = card reorder, horizontal swipe = column navigation, with a threshold angle)
2. Consider using a gesture library like `@use-gesture/react` for unified touch handling

---

### P1-10: Background Tab Timer Throttling

**Source:** [ReminderEngine.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/ReminderEngine.jsx)
**Current behavior:** Uses `setInterval(..., 60000)` for reminder checks. Browsers aggressively throttle `setInterval` in background tabs (Chrome: minimum 1 minute; some browsers: up to 10 minutes).
**Impact:** Reminders may fire significantly late if the user switches to another tab. Combined with the 60-second granularity, a reminder could be up to 10+ minutes late.
**Solution:**
1. Use the `visibilitychange` event to immediately check for due reminders when the tab regains focus
2. Rely on server-side push notifications as the primary delivery mechanism for time-critical reminders (already partially implemented)
3. Consider using `navigator.scheduling` API or `requestIdleCallback` for non-critical checks

---

### P1-11: Confetti Fires on Un-completion

**Source:** [TaskCard.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/TaskCard.jsx)
**Current behavior:** The confetti celebration and audio chime trigger on every completion toggle — including when a user **un-completes** a task (marks it as incomplete again).
**Impact:** Semantically wrong feedback. Celebrating an "undo" is confusing and erodes the meaning of the celebration. Violates the spirit of GEMINI.md §6 Rule 5 ("Recompensa al usuario sutilmente al **completar** hábitos").
**Solution:** Add a guard: only trigger confetti/sound when transitioning from `is_completed: false` → `true`, not on the reverse toggle.

### P2-2: No Undo for Destructive Actions

### P2-4: InlineTaskForm — No Auto-Focus, No Escape-to-Cancel

### P2-5: Review Modal — No Progress Persistence, No Focus Trap

**Source:** [PeriodicReviewModal.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/PeriodicReviewModal.jsx)

### P2-6: No Service Worker Update Prompt

**Source:** [sw.js](file:///Users/jaimehmol/src/habits-app/frontend/src/sw.js), [vite.config.ts](file:///Users/jaimehmol/src/habits-app/frontend/vite.config.ts)
**Current behavior:** When a new service worker is deployed, the update happens silently on the next visit. Users may be running stale code for extended periods.
**Impact:** Bug fixes and new features may not reach users promptly. Critical fixes to push notification logic (documented in [push-notification-fixes.md](file:///Users/jaimehmol/src/habits-app/docs/2026-07-21-push-notification-fixes.md)) may be delayed.
**Solution:** Add an in-app banner/toast: "A new version is available. [Refresh]" triggered by the `controllerchange` event on the service worker registration.

### P2-7: No Request Timeout or Retry Logic in API Client

**Source:** [api.js](file:///Users/jaimehmol/src/habits-app/frontend/src/services/api.js)
**Current behavior:** `fetch()` calls have no timeout. On slow networks, the UI hangs indefinitely. Failed requests are not retried.
**Impact:** On flaky mobile connections, the user sees an indefinite loading state with no feedback.
**Solution:**
1. Add `AbortController` with a 10-second timeout to all fetch calls
2. Add retry logic (1-2 retries with exponential backoff) for idempotent operations (GET, PATCH)
3. Show a timeout-specific error message: "Connection timed out. Check your network"

### P2-8: Number Input Spinners Hidden in CSS

**Source:** [index.css](file:///Users/jaimehmol/src/habits-app/frontend/src/index.css)
**Current behavior:** CSS hides the native increment/decrement arrows on `<input type="number">`.
**Impact:** Removes a standard affordance for keyboard-only users and those with motor disabilities who rely on the step buttons.

### P2-9: Push Permission Requested Without Context

**Source:** [pushSubscription.js](file:///Users/jaimehmol/src/habits-app/frontend/src/services/pushSubscription.js)
**Current behavior:** Calls `Notification.requestPermission()` directly, triggering the browser's native permission prompt without first explaining to the user why notifications are needed.

**Solution:** Show a custom in-app prompt first (e.g., "Enable notifications to receive habit reminders?") with a clear benefit statement. Only trigger the browser prompt after the user taps "Enable".

### P2-10: Notification Toast Has No Stacking/Queue

### P2-11: Dense Touch Targets on Mobile Task Cards

**Source:** [TaskCard.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/TaskCard.jsx)

### P2-12: Color-Only Priority Indication

### P3-8: `datetime.utcnow()` Deprecation Warning

**Source:** Backend [models.py](file:///Users/jaimehmol/src/habits-app/backend/src/domain/models.py)
**Impact:** Python 3.12+ emits deprecation warnings. Will be removed in future Python versions.
**Solution:** Replace `datetime.utcnow()` with `datetime.now(timezone.utc)`.

### P3-9: No API-Level (Router) Tests

**Source:** [backend/tests/](file:///Users/jaimehmol/src/habits-app/backend/tests)
**Current behavior:** Only service-level unit tests exist. No tests using FastAPI's `TestClient` for endpoint-level testing.
**Impact:** Router-level logic (auth middleware, request parsing, response formatting, error mapping) is untested.
**Solution:** Add integration tests using `TestClient` for all routers.

### P3-10: Mixkit External URL for Notification Sound

**Source:** [ReminderEngine.jsx](file:///Users/jaimehmol/src/habits-app/frontend/src/components/ReminderEngine.jsx)
**Current behavior:** References an external Mixkit URL (`SLACK_SOUND_URL`) for notification audio.
**Impact:** Depends on third-party CDN availability. If Mixkit is down or the URL changes, notifications play silently. Also contradicts the offline-first philosophy.
**Solution:** Bundle the audio file locally in `/public/sounds/` or synthesize it using Web Audio API (consistent with the confetti completion sound approach).

### P3-11: N+1 Query Pattern in Reorder/Reset Operations

**Source:** Backend task service
**Current behavior:** `reorder_tasks` and `reset_daily_tasks` fetch objects and issue an individual `UPDATE` query per task in a loop.
**Impact:** With 50+ tasks in a column, reordering generates 50 DB round-trips.
**Solution:** Use bulk SQL `UPDATE` with CASE expressions or batch sessions.
